Devion Frontend Stack

Referenz für alle Libraries im Devion-Frontend (apps/web) — was sie tun, warum wir sie gewählt haben, und wie sie bei uns konkret verwendet werden. Bei Fragen zu einer neuen Library: erst hier nachschauen, dann im Team-Channel fragen.

Stack: Next.js · Bun · TypeScript
Scope: Nur Frontend (apps/web)
Bun
Runtime

JavaScript-Runtime, Package-Manager und Bundler in einem. Ersetzt bei uns Node.js + npm/pnpm komplett.

Install 
# Windows (PowerShell)
powershell -c "irm bun.sh/install.ps1 | iex"

Warum wir es nutzen

  • Deutlich schnellere Installs & Cold-Starts als npm/yarn/pnpm
  • Nativer TypeScript-Support ohne ts-node o.ä.
  • Ein Tool für Runtime, Package-Manager, Test-Runner und Bundler statt vier separater

Befehle, die wir nutzen

bun install
bun add react-hook-form
bun add -d shadcn
bun remove swr
bun run dev
bun run src/test.ts
Team-Konvention: Immer bun statt npm/yarn nutzen — gemischte Lockfiles (package-lock.json neben bun.lockb) verursachen inkonsistente Installs im Team.

TypeScript
Sprache

Statisch typisiertes JavaScript. Durchgängig im gesamten Monorepo — Frontend, Backend, Config-Packages.

Warum strikt wichtig ist

Bei Multi-Tenant-Logik (Org → Team → Project) verhindert strikte Typisierung, dass z.B. eine orgId versehentlich mit einer teamId vertauscht wird — beides ist als string technisch kompatibel, aber fachlich komplett unterschiedlich.

Unser Standard in tsconfig.json

{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "paths": { "@/*": ["./src/*"] }
  }
}
Next.js (App Router)
Frontend-Framework

Reines Frontend bei uns — kein eigenes Backend im Next-Projekt. Übernimmt Routing, Layouts und Rendering.

Wichtige Konzepte

  • page.tsx = Route, layout.tsx = persistenter Wrapper
  • (gruppe) Ordner = Route Group, taucht nicht in der URL auf
  • [param] = dynamisches Segment, z.B. [orgSlug]
Team-Konvention — kein RSC: Wir nutzen bei Devion bewusst keine Server Components. Alle Daten kommen über Hono RPC + TanStack Query vom Backend, Next.js ist reine UI-Schicht. Deshalb bekommt jede page.tsx und layout.tsx ohne Ausnahme 'use client' als erste Zeile — keine Fallunterscheidung nötig, kein Debugging wegen vergessener Direktive.

Beispiel: org-scoped Route

app/(org)/[orgSlug]/projects/[projectId]/page.tsx 
'use client' // immer, ausnahmslos

import { useProject } from '@/features/projects/hooks'

export default function ProjectPage({
  params,
}: {
  params: { orgSlug: string; projectId: string }
}) {
  const { data: project, isLoading } = useProject(params.projectId)

  if (isLoading) return <ProjectSkeleton />

  return <ProjectOverview project={project} />
}

Beispiel: Org-Layout ohne Server-Fetch

app/(org)/[orgSlug]/layout.tsx 
'use client'

export default function OrgLayout({
  children,
  params,
}: {
  children: React.ReactNode
  params: { orgSlug: string }
}) {
  const { data: org, isLoading } = useOrgBySlug(params.orgSlug)
  const { data: membership } = useCurrentMembership(org?.id)

  if (isLoading) return <FullPageSpinner />
  if (!org) return <NotFoundState />
  if (!membership) return <NoAccessState />

  return (
    <OrgProvider org={org} membership={membership}>
      <Sidebar variant={'org'} />
      <main>{children}</main>
    </OrgProvider>
  )
}
Zugriffsschutz ohne redirect(): redirect()/notFound() aus next/navigation sind Server-Funktionen und funktionieren in Client Components nur eingeschränkt. Stattdessen: Empty/Error-State direkt rendern, oder router.push() in einem useEffect. middleware.ts bleibt davon unberührt — läuft immer im Edge-Runtime und ist unser eigentliches Auth-Gate vor dem ersten Render.

Beispiel: Navigation im Code

import Link from 'next/link'
import { useRouter } from 'next/navigation'

<Link href={`/${orgSlug}/projects`}>Projekte</Link>

const router = useRouter()
router.push(`/${orgSlug}/projects/${projectId}`)

Hono RPC (hono/client)
Typsicherer API-Client

Der einzige Weg, wie das Frontend mit dem Backend spricht — typsicher, ohne OpenAPI-Codegen. Ersetzt fetch() im gesamten Frontend.

Der AppType kommt aus dem Backend-Repo (@devion/api) — wird nur als Typ importiert, kein Backend-Code landet im Frontend-Bundle.

Setup

lib/api-client.ts 
import { hc } from 'hono/client'
import type { AppType } from '@devion/api'

export const client = hc<AppType>(
  process.env.NEXT_PUBLIC_API_URL!,
  { init: { credentials: 'include' } }
)

Wichtig zu verstehen

Hono RPC ist nicht dasselbe wie TanStack Query. Der RPC-Client macht nur den einzelnen, typsicheren Request — Caching, Retry und Loading-States kommen von TanStack Query obendrüber. Beide werden immer zusammen genutzt, nie als Alternative zueinander.

Nutzung

const res = await client.api.orgs[':orgId'].projects.$get({
  param: { orgId }
})
if (!res.ok) throw new Error('Fehler beim Laden')
const projects = await res.json() // voll typisiert

TanStack Query
Server-State

Verwaltet jeden API-Call: Caching, Refetching, Loading/Error-States, Invalidation. Das Rückgrat unseres Data-Fetchings.

bun add @tanstack/react-query

Query-Keys — immer org-scoped

Bei Multi-Tenancy muss die orgId im Query-Key stehen, sonst leaked der Cache zwischen Organisationen beim Wechsel.

lib/query-keys.ts 
export const queryKeys = {
  orgs: {
    projects: (orgId: string) => ['orgs', orgId, 'projects'] as const,
  },
}

Standard-Hook-Pattern

export function useProjects(orgId: string) {
  return useQuery({
    queryKey: queryKeys.orgs.projects(orgId),
    queryFn: () => fetchProjects(orgId),
    enabled: !!orgId,
  })
}

Mutation + Invalidation

export function useCreateProject(orgId: string) {
  const queryClient = useQueryClient()
  return useMutation({
    mutationFn: createProject,
    onSuccess: () => {
      queryClient.invalidateQueries({
        queryKey: queryKeys.orgs.projects(orgId)
      })
    },
  })
}
Team-Konvention: swr wurde bewusst entfernt — wir nutzen ausschließlich TanStack Query für Server-State, nie beides parallel.

TanStack Table
Tabellen-Logik

Headless — liefert nur die Logik (Sorting, Filtering, Pagination), das UI bauen wir selbst mit shadcn's Table-Komponenten.

Wo wir es einsetzen

  • Projects-, Hardware-, Members-, Audit-Log-Tabellen
  • Column-Definitions sind vollständig typsicher basierend auf dem API-Response-Typ

Beispiel: Server-Tabelle

features/hardware/components/node-table.tsx 
const columns: ColumnDef<Node>[] = [
  {
    accessorKey: 'name',
    header: 'Name',
  },
  {
    accessorKey: 'status',
    header: 'Status',
    cell: ({ row }) => <NodeStatusBadge status={row.original.status} />,
  },
  {
    accessorKey: 'cpuUsage',
    header: 'CPU',
    cell: ({ row }) => `${row.original.cpuUsage}%`,
  },
]

export function NodeTable({ data }: { data: Node[] }) {
  const table = useReactTable({
    data,
    columns,
    getCoreRowModel: getCoreRowModel(),
    getSortedRowModel: getSortedRowModel(),
  })

  return (
    <Table>
      <TableHeader>
        {table.getHeaderGroups().map((hg) => (
          <TableRow key={hg.id}>
            {hg.headers.map((h) => <TableHead key={h.id}>...</TableHead>)}
          </TableRow>
        ))}
      </TableHeader>
      <TableBody>
        {table.getRowModel().rows.map((row) => (
          <TableRow key={row.id}>...</TableRow>
        ))}
      </TableBody>
    </Table>
  )
}

React Hook Form
Formulare

Uncontrolled-by-default — kaum Re-Renders, auch bei komplexen Multi-Step-Forms wie dem Datenbank-Provisioning-Wizard.

bun add react-hook-form @hookform/resolvers

Beispiel: Login-Form mit Zod-Validation

features/auth/components/login-form.tsx 
const loginSchema = z.object({
  email: z.string().email('Ungültige E-Mail'),
  password: z.string().min(8, 'Mindestens 8 Zeichen'),
})

type LoginInput = z.infer<typeof loginSchema>

export function LoginForm() {
  const form = useForm<LoginInput>({
    resolver: zodResolver(loginSchema),
    defaultValues: { email: '', password: '' },
  })

  const { mutate, isPending } = useLogin()

  function onSubmit(values: LoginInput) {
    mutate(values)
  }

  return (
    <Form {...form}>
      <form onSubmit={form.handleSubmit(onSubmit)}>
        <FormField
          control={form.control}
          name={'email'}
          render={({ field }) => (
            <FormItem>
              <FormLabel>E-Mail</FormLabel>
              <FormControl><Input {...field} /></FormControl>
              <FormMessage />
            </FormItem>
          )}
        />
        <Button type={'submit'} disabled={isPending}>
          Anmelden
        </Button>
      </form>
    </Form>
  )
}

Tailwind CSS v4
Styling

Utility-First-CSS, Basis für unser gesamtes Design-System zusammen mit shadcn.

v4-Hinweis: Konfiguration läuft über CSS (@theme), nicht mehr über tailwind.config.js wie in v3.

Beispiel: Status-Badge mit cn()

function NodeStatusBadge({ status }: { status: 'online' | 'offline' }) {
  return (
    <span
      className={cn(
        'inline-flex items-center gap-1.5 rounded-full px-2.5 py-0.5 text-xs',
        status === 'online'
          ? 'bg-emerald-500/10 text-emerald-400'
          : 'bg-zinc-800 text-zinc-500'
      )}
    >
      {status}
    </span>
  )
}

shadcn/ui
Komponenten

Kein NPM-Package im klassischen Sinn — Komponenten werden per CLI generiert und liegen als eigener Code im Repo unter components/ui/.

Warum das wichtig ist

Volle Kontrolle über den Komponenten-Code — keine Blackbox-Library. Anpassungen passieren direkt am generierten Code, nicht über Props-Overrides einer fremden Library.

bunx shadcn@latest add table dialog dropdown-menu chart

Beispiel: generierte Komponente nutzen

import { Dialog, DialogContent, DialogTrigger } from '@/components/ui/dialog'
import { Button } from '@/components/ui/button'

<Dialog>
  <DialogTrigger asChild>
    <Button>Node verbinden</Button>
  </DialogTrigger>
  <DialogContent>
    <ConnectNodeWizard />
  </DialogContent>
</Dialog>

better-auth/client
Auth-Client

Der Client-Teil von better-auth — im Frontend zuständig für Login, Register, Session-Handling und Org-Switching. Die eigentliche Auth-Logik (DB-Adapter, Plugins) liegt im Backend, nicht hier.

Setup im Frontend

import { createAuthClient } from 'better-auth/client'
import { organizationClient } from 'better-auth/client/plugins'

export const authClient = createAuthClient({
  baseURL: process.env.NEXT_PUBLIC_API_URL,
  plugins: [organizationClient()],
})

Nutzung in Komponenten

const { data: session } = authClient.useSession()

await authClient.signIn.email({ email, password })
Wichtig: Immer better-auth/client als Subpath-Import aus dem Hauptpaket better-auth nutzen. Das alte, separate @better-auth/client-Package (Alpha-Stand) wird bei uns nicht mehr verwendet.
